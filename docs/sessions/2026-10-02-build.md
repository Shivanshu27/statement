# 2026-10-02 — Building Statement, M0 to M8

What broke, how it was noticed, and what I wrongly believed first. These
entries are the reason the corresponding tests and guards exist.

---

## 1. The forge produced a silently wrong statement — and the verifier accepted it

**Symptom.** In the first Tier-1 smoke run, 13 of 15 `ledger_split`
documents were `ACCEPTED`, but their descriptions did not match truth:

```
got   UPI/681678096427/STARBUCKS/PAYMEN6T752151005854466 FROM PHONE
want  UPI/681678096427/STARBUCKS/PAYMENT FROM PHONE
```

**Wrong first hypothesis.** A bug in the column-assignment code in Tier 1.

**Actual cause.** A forge geometry bug. The long `UPI/…/PAYMENT` token has
no spaces, so word-wrap could not break it. It overflowed the Narration
column into the reference column. Overlapping text makes pdfplumber
interleave characters from the two columns (`PAYMEN` + `6` + `T` + the
reference digits). On the paren_negative layout the same bug put the word
`AND` into the Amount column, which at least failed loudly as
`UNPARSEABLE_MONEY`.

**Why it matters more than a forge bug.** The arithmetic was untouched, so
the balance chain held and the documents were accepted. This is §B5
happening for real on day one: description corruption is invisible to L2.
Without the L3 scorer, it would have shipped as "100% accepted".

**Fixes.**
- The forge now *refuses* to draw text wider than its column (`ValueError`,
  test `test_overflowing_text_is_a_forge_bug`). Overlapping text is a
  generator bug, not a test case.
- The description width now accounts for how far Tier 1 lets right-aligned
  values reach left of their header.
- UPI descriptions gained a space so they can wrap.

## 2. Header midpoints are the wrong column boundaries

**Symptom.** Found while designing the fix for #1. Boundaries placed midway
between header labels cut a wide left-aligned Narration column in half,
because the narration runs far past its header.

**Fix.** Boundaries now depend on alignment (`Column.align`, defaulting to
right for amounts). The boundary before a left-aligned column sits just
before its header. The boundary before a right-aligned column allows values
to reach up to one header-width (minimum 40pt) to its left.

## 3. `TypeError` escapes pydantic validators

**Symptom.** `test_no_float_reaches_money` expected a `ValidationError` and
got a raw `FloatMoneyError` traceback.

**Cause.** Pydantic converts only `ValueError`/`AssertionError` raised in
validators. `FloatMoneyError(TypeError)` crashed model construction instead
of failing the field. This also mattered for the corruption harness, which
catches `ValidationError` to count "detected by construction".

**Fix.** `FloatMoneyError` is now a `ValueError`. The field name now appears
in the error.

## 4. The prompt-injection fixture grounded a hallucination test

**Symptom.** `test_rescued_amounts_are_grounded` claimed that the invented
closing balance `9999999.00` was flagged as ungrounded. It wasn't.

**Cause.** That sample contains the forge's F11 injection fixture, whose text
literally includes `9999999.00`. The number *was* on the page, so grounding
correctly accepted it. (The verifier still rejected the document on
`TOTALS_MISMATCH`, which is the other half of the defence.)

**Fix.** The test now invents a number that appears nowhere (`8888888.00`).
A separate test, `test_prompt_injection_cannot_move_a_number`, covers the
"obey the injection" case on purpose.

**Lesson.** Grounding proves a number *is printed*, not that it is *the right
number*. That is why INV-05 and INV-06 are separate invariants.

## 5. Carry-forward dates can't be grounded on their own row

**Found while** writing the Tier-2 oracle. Layouts that print a date only on
a day's first row (drcr_suffix) have later rows with no date text. A strict
"every value appears on its row's lines" rule would reject a perfect
transcription.

**Decision.** A *date* may be grounded on an earlier line of the same page.
Amounts and balances must still appear on the row's own lines.
Recorded as a deviation in ARCHITECTURE.md.

## 6. Risk R1 tripped: Tier 1 scored 100% on everything

**Symptom.** Dev corpus: 160/160 exact. That was the plan's tripwire for
"synthetic corpus too clean".

**Cause.** The profiles were written knowing the layouts, so a perfect score
measures only self-consistency.

**Response.** Added a `drift` split: the same four banks after a template
change (renamed headers, a dropped column). This is how header-keyed parsers
break in production. Tier 1 goes to **0% coverage with 0 silent-wrong** on
it: loud failure, as designed. Recovering those documents is Tier 2's job
(H3), which needs a real model to measure.

## 7. An ambient `ANTHROPIC_BASE_URL` was set on the build machine

**Noticed** while checking the environment. Another tool on the machine
points this variable at its own endpoint. An adapter that honoured it would
silently send statement text there.

**Fix.** Adapters read only `STATEMENT_*` variables (`STATEMENT_LLM_BASE_URL`,
`STATEMENT_ANTHROPIC_API_KEY`), never the ambient ones. The reason is noted
in the module docstring.

## 8. "Closing Balance" is both a label and a column header

**Found** while writing the ledger_split profile. Label search takes the
first line containing the label, which is the table header, with no amount
after it. The summary block prints `Closing Bal :`. The profile uses that.
This is the kind of thing the onboarding skill's S2 table warns about.

## 9. Onboarding iteration 1 hit the anti-goal case exactly

See `docs/onboarding/split_zero_filled.md`. The v1 profile scored 100%
coverage with 2 silent-wrong documents: a bank notice was appended to
descriptions. Coverage said "done". Only row agreement showed it wasn't.

## 10. No git repository

The build ran in a plain folder, by instruction (no commits without asking).
Consequences:
- Manifests record `git_sha: not-a-git-repo`.
- The skill's `git stash` regression step was done by diffing saved replay
  dumps.
- `check_no_pdfs.py` falls back to scanning the working tree.

Running `git init` and making a first commit is the first step after this
session.

## 11. A flaky CLI test was a real collision bug

**Symptom.** `test_cli_round_trip` passed under `pytest -q` and failed under
plain `pytest` with `FileExistsError`.

**Wrong first hypothesis.** Test pollution between runs.

**Cause.** Run directories were named by UTC second. The test ran `eval`
twice within one second, and the second run crashed instead of writing its
scorecard. Anyone scripting two evals back to back would have hit the same.
Timing differences between the two invocations decided whether it showed up.

**Fix.** `_run_dir` suffixes `-1`, `-2`, … on collision. It never overwrites
an existing run. Lesson recorded: a flaky test is a bug report with bad
timing.

## What was *not* done (and must not be claimed)

- **No real LLM was called.** No API key was configured, and a local model
  would have meant installing software on the machine. Tier 2 was exercised
  only with scripted test doubles: a perfect "oracle" transcriber and
  adversarial variants. **H2-for-Tier-2, H3 and H5 are unmeasured.**
- **The CI workflows have never run.** They are written but untested until
  the repo is pushed.
- **H4 was not a blind trial** (see the onboarding report).
